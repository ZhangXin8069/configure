# team — 持续协作编排技能

## 执行前置

遵循当前目录 `AGENTS.md`「技能执行公共契约」；仅按需读取技能正文与 reference。

team 负责跨轮协作与 worker 生命周期，不替代具体领域技能。若只是一次性的独立子任务拆分，
转 `dispatch`；若只是单线程循环收敛，转 `all`；若只是无人值守包装，转 `auto`；若只是续接
中断后的上下文，转 `go-on`。

本技能吸收用户指定的 [muIon-beam team skill](https://gitee.com/chx6/muIon-beam/tree/db48dcbed023a427c5b87231451b5392c6e65684/.codex/skills/team)
的通用原则；仅保留能力匹配、单文件单写者和只读审查者约束，不引入其项目路径或运行时记录目录。

## 核心原则

1. **先画状态机，再开 worker**：长期任务最容易在等待、回退和重试中丢上下文，先把阶段、退出条件和回跳条件写清，后续才知道何时重派、何时收尾。
2. **一 worker 一隔离线**：每个 worker 只写自己的 git worktree / 临时目录 / 产物前缀，避免共享可变状态把责任混在一起。
3. **拆解按依赖图，不按直觉**：独立子图才并行，依赖链必须串行，判断不清时先合并，不冒险拆散。
4. **指令必须自包含**：worker 不能依赖会话历史，必须拿到问题域、目标、约束、允许改动的文件/目录、预期输出和停止条件。
5. **先发现能力再分派**：在可用时读取运行器的模型、推理级别和工具兼容性，按问题能力与资源约束选择最小足够 worker；不默认使用最高档能力。
6. **单文件单写者**：每个文件只允许一个 worker 负责写入，审查者默认只读；子 worker 不得继续派生 worker，除非父目标明确授权。
7. **健康检查看证据，不看口头承诺**：心跳、退出码、diff、日志新鲜度、重复失败模式比“我大概做完了”更可靠。
8. **失败先分类，再重派或合并**：先判断是依赖未解、范围太大、上下文不足、实现偏航还是隔离污染，再决定缩小重派、顺序化还是回收隔离。
9. **收敛前先整合且不重复领域方法**：每个 worker 的结果都要回到同一验收线下复查；真正的修复、测试、优化和审查仍交给具体技能，team 负责调度、隔离、监控和收尾。

## Git 检查

有 Git 且本次产生文件改动时，执行 `git diff --check` 和定向复查；多工作树任务先在各自工作树检查，再在集成树复查。未经用户明确要求不自动暂存、提交或推送；无 Git 或无改动时跳过。

## 触发时机

- 用户说“持续协作”“worker 调度”“状态机”“工作树隔离”“健康检查”“失败重派发”“长期任务编排”“多轮协作”
- 任务不是一次性拆域，而是需要多轮跟踪、失败替换、阶段推进和最终收敛
- 与其他技能配合：一次性并行拆域用 `dispatch`；收敛循环用 `all`；无人值守包装用 `auto`；会话续接用 `go-on`；worker 自己的具体工作交给 `debug` / `test` / `optim` / `diff`
- team 可以调用 `dispatch` 做某一批次的并行拆域，但不会把整个任务降成一次性并行
- 不适用：只有一个批次的独立子任务、没有状态机需要、无需 worker 复活/监控的简单并行 → 用 `dispatch`

## 工作流程

### Step 1. 定义目标与收敛条件

一次性收集并确认任务对象、交付物、验收标准、允许修改范围、时间/资源预算、失败后是否允许重派。
缺项先问全，不逐次追问。输出一句任务定义和收敛线。

### Step 2. 画状态机

把任务拆成：

```text
intake -> decompose -> isolate -> dispatch -> monitor -> health-check
health-check -> integrate   (健康)
health-check -> recover     (卡住/越界/失联)
recover -> dispatch         (局部重派)
recover -> decompose        (依赖图有误)
integrate -> converge -> finalize
```

写出每个状态的退出条件和回跳条件。依赖关系不清时，先停在 `decompose`，不要提前开 worker。

### Step 3. 建立隔离工作线

对每个 worker 分配独立 git worktree；无 Git 时用独立临时目录和独立产物前缀。优先采用：

```bash
git worktree add ../team-<worker-id> <base-branch>
```

记录 worker id、负责域、允许改动的文件、依赖、预期结果、回收方式和能力选择理由。明确每个文件的唯一写者；任何两个 worker 只要可能改同一文件，就不要并行。

### Step 4. 派发首批 worker

用当前运行器可用的 worker / task / 子代理机制发起首批任务。每个 worker 指令至少包含：

- 问题域
- 目标
- 约束
- 预期输出
- 心跳或回报频率
- 终止条件

必要时先派一个探索 worker 定位依赖或风险，再决定是否继续拆分。首批派发可直接复用 `dispatch` 的拆域思路，但 worker 生命周期由 `team` 继续管理；审查 worker 默认只读，子 worker 不得自行扩展派发范围。

### Step 5. 健康检查与重派

每轮检查 worker 的进展、日志新鲜度、diff、退出码和重复错误模式。健康则继续；卡住则先判断是依赖缺失、范围过大、上下文不足还是隔离失败。

能缩小就重派更小域；依赖缠在一起就合并后顺序执行；污染工作树就回收并重建隔离。不要让 worker 在共享树里静默推进。

### Step 6. 汇聚与收尾

所有 worker 返回后先做冲突检查，再做集成验证，再做抽查。只有在实测通过、冲突清零、残余风险可说明时才宣布收敛。

最后输出：状态机结果、worker 摘要、重派记录、验证命令、遗留项。

## 错误处理

| 场景 | 处理 |
|---|---|
| 只有一次并行就够 | 转 `dispatch`，不要用 `team` 维持 worker 池 |
| 依赖关系不清或多个 worker 可能改同一文件 | 合并域，重画状态机，改为顺序执行 |
| worker 长时间无心跳或同错重放 | 判失败，缩域重派或回收该 worker |
| 工作树污染 / 串写 | 停止扩散，重建隔离后再继续 |
| worker 输出无证据 | 以实测为准，要求补证据或重派 |
| 集成验证失败 | 回到最近稳定点，按 `debug` / `test` 修复后再合并 |
| 任务目标变化 | 重新定义状态机和工作树，重算派发 |
| 最终结果只在单个 worker 内成立 | 不算收敛，必须回到集成树复验 |

## 注意事项

- 这是编排技能，不是领域技能。
- 能顺序就别并行；能合并就别硬拆。
- worker 的“完成”必须能在文件、日志或命令输出里复核。
- 如果工作树隔离做不到，先降级为顺序流程，不要假装并行。
