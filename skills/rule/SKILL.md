# rule — 进程、资源与条件式交付常驻规则

## 执行前置

遵循当前目录 `AGENTS.md`「技能执行公共契约」；只加载当前阶段需要的参考文件。

`rule` 是常驻辅助技能：用户未明确说明“关闭 rule”“不应用 rule”时，它与 `log` 一同随任一被调用的
技能启用。常驻不等于逐命令创建日志，只在以下门控点执行：

- 启动命令、后台进程、子 agent 或调度作业之前；
- 监控长任务、判断停滞或终止异常进程时；
- 在共享环境分配资源或提交到计算节点之前；
- 阶段性成果准备提交到本地或远程 Git 时。

`rule` 不替代 `debug`、`optim`、`test`、`dispatch`、`team`、`tag` 或 `log` 的领域流程，只负责把资源、
时间、可观测性和交付安全约束注入这些流程。

详细参考：

- `references/process-and-resources.md`：进程预算、共享环境、调度器和终止流程。
- `references/conditional-delivery.md`：条件式自动提交、推送和标签判定。
- `references/extracted-rules.md`：从本目录其他技能抽取并统一后的规则映射。
- `scripts/run-guarded.sh`：带硬超时、心跳、进度文件新鲜度检查和日志的进程守卫。
- `scripts/run-guarded.test.sh`：进程守卫回归测试。

## 核心原则

1. **无预算不启动**：每个 agent 发起的命令、后台任务、子 agent 和调度作业都要有可执行的时间与资源
   预算。无界运行会把局部错误放大成整个任务的阻塞，也会长期占用共享资源。
2. **长任务必须可观测**：预计超过 10 分钟的进程必须有启动记录、周期心跳、任务级进度、结束状态和退出码。
   只有“进程还活着”不足以证明工作正常，必须同时观察真实进展、资源曲线和检查点。
3. **共享环境使用最小充分资源**：环境不明确时按共享环境处理。登录节点只做编排和轻量操作，重计算进入
   调度器；并发、CPU、内存、GPU、磁盘和网络都按最小充分原则限制。
4. **调度作业显式校准资源规格**：队列、运行时长、节点、任务数、CPU、内存、GPU、临时盘和输出都必须明确，
   并用小规模试跑或历史数据校准。不能依赖集群默认值或省略限制。
5. **必要资源不打折**：若实测证明任务必须使用较大资源，就为完整正确的结果分配足够预算；不得为了节省
   机时、磁盘或费用而截断规模、降低精度、省略验证或交付不完整结果。
6. **异常进程先取证再中断**：无进展、超时、资源异常或错误重放时，先读取日志、进程状态和资源指标，区分
   可续任务与失效进程；先软终止并等待检查点，再强制清理，随后进入充分 debug/optim。
7. **交付必须形成同步闭环**：只有阶段验收通过、改动范围清楚、功能无回归、无敏感信息或超限文件、远程分支
   可 fast-forward 时，才允许按本技能的条件式授权自动提交和推送。本次本地提交或标签已经形成且全部闸门仍
   通过时，“尚未推送”不是终态；必须继续推送当前分支和本次新标签。只有推送失败、无远程、用户明确要求仅
   本地或闸门不满足时，才可报告未推送并停止。
8. **常驻但克制**：规则在启动、监控、资源分配和交付门控点生效，不干预普通只读查询，也不把每次命令都
   变成正式日志。
9. **证据先于结论**：超时、停滞、资源浪费、可安全提交和可推送等判断都必须基于本次运行的命令输出、
   退出码、指标和 Git 状态，不使用“看起来正常”或“应该没问题”。

## Git 检查

默认仍遵循仓库公共契约：任务改动必须执行 `git diff --check` 与定向复查，未经授权的普通改动不自动暂存、
提交、推送或打标。

本技能包含用户明确授予的**条件式自动交付规则**：阶段性改动同时满足
`references/conditional-delivery.md` 的全部闸门时，可直接提交到本地和当前远程分支，并按 `tag` 技能
创建非破坏性注释标签，无需再次请求用户确认。此授权不包含 force push、改写或删除已推送标签、仓库外写入、
系统配置、凭据操作或超过 `10,000,000` 字节闸门的文件；任一条件未知或不满足时停止自动交付并保留证据。

`~tag:<type>` 或等价标签交付请求默认同时授权条件式远程同步，除非用户明确要求仅本地。因此，当本地提交和
标签已存在、全部闸门通过且远程可 fast-forward 时，不得以“尚未推送，如需同步请执行……”结束任务；必须
先推送当前分支，再推送本次新标签并回读验证。

有任何本次文件改动时至少执行：

```bash
repo_root=$(git rev-parse --show-toplevel)
git -C "$repo_root" diff --check
git -C "$repo_root" status --short
```

## 触发时机

- 启动任何可能运行较久、占用较多资源、产生大量输出或后台运行的命令；
- 预计运行超过 10 分钟，或实测已超过原估算、出现心跳缺失、进度停滞和重复错误；
- 在服务器登录节点、共享工作站、容器宿主、教学机或其他多人共享环境执行任务；
- 使用 Slurm、PBS、LSF、SGE 等调度器向计算节点提交作业；
- 需要派发子 agent、worker 或长时测试，并监控其健康状态；
- 阶段成果已完成，需要判断是否自动提交、推送或创建 `dev/stab/bug/test` 标签；
- 用户直接说“进程限时”“资源限制”“别占满机器”“检查是否卡住”“自动提交”“按 rule 执行”。

与其他技能配合：

- `debug`：异常进程中断后先复现和定位根因，禁止只重跑；
- `optim`：确认逻辑正确后处理性能、内存、IO 和并发瓶颈；
- `test`：为阶段性自动交付提供本次会话的通过证据；
- `diff`：交付前检查范围、冲突标记、调试残留和未跟踪文件；
- `form`：提交前执行目录/命名检查和 `10,000,000` 字节大文件闸门；
- `dispatch` / `team`：给子 agent 和 worker 传递同样的时间、资源、心跳与停止条件；
- `go-on`：续接任务前先检查孤儿进程，但不中断仍有价值且可续接的进程；
- `tag`：满足交付闸门且标签类型明确时创建非破坏性注释标签；
- `log`：在阶段成果和任务完成门控点归档日志与全文报告。

不适用：无需启动进程的纯文字回答、普通只读查询，以及用户明确关闭 `rule` 的当前任务；更高优先级的安全
边界仍然有效。

## 工作流程

### Step 1. 判定环境并建立进程预算

启动前先判定运行环境和任务类别：

| 环境 | 判定信号 | 默认策略 |
|---|---|---|
| 独占本地 | 用户明确说明独占，且无调度器/共享迹象 | 使用最小充分资源；仍设置硬超时 |
| 共享交互 | 登录节点、共享工作站、多人服务器或环境未知 | 单线程、低优先级、低并发；禁止未调度重计算 |
| 调度作业 | `sbatch`/`qsub`/`bsub` 等入口可用，或用户指定集群 | 所有资源、队列和运行时长显式声明 |
| 子 agent/worker | 通过 `agent-dispatch.sh` 或运行器 task 机制派发 | 任务提示中写入预算、心跳、输出路径和停止条件 |

为每个进程写出并传递 `process_budget`：

```text
label=<唯一名称>
environment=<local-exclusive|shared-interactive|scheduler|remote-worker>
estimated_duration=<预计时长及依据>
soft_deadline=<开始排查异常的时点>
hard_timeout=<强制终止上限>
heartbeat=<心跳间隔；>10 分钟任务必须有>
progress_signal=<阶段计数/迭代数/文件更新/检查点/输出日志>
stale_after=<无进展判定阈值>
cpu=<核数或线程上限>
memory=<RSS/内存上限>
gpu=<型号/数量/显存上限>
disk=<临时盘与输出上限>
concurrency=<并发进程/作业数>
queue=<调度队列或分区；调度任务必填>
cleanup=<进程、临时文件和失败产物清理方式>
```

预算确定规则：

1. 优先用同输入基线、历史运行或小规模试跑估算；没有数据时先执行有硬上限的探测。
2. `hard_timeout` 必须非空且有限，通常取实测/估算上界加上合理余量，并受任务总截止时间约束。
3. `>10 分钟` 的任务必须启用进度日志；默认心跳不超过 60 秒，`stale_after` 初值取 3 个心跳周期，
   再按任务真实进度调整。单个原子步骤无法频繁输出时，由外层心跳配合每步开始/结束记录。
4. 所有工具调用同时设置工具级超时；需要操作系统级兜底时使用 `timeout` 或等价机制。
5. 无法形成有限预算时，不启动该进程；先拆分、试跑或报告阻塞原因。

需要确定性守卫时调用：

```bash
RULE_SKILL_DIR=${RULE_SKILL_DIR:-$HOME/configure/skills/rule}
process_log=${process_log:-$PWD/.agent.rule-process.log}
event_log=${event_log:-$PWD/.agent.rule-events.log}

"$RULE_SKILL_DIR/scripts/run-guarded.sh" \
  --label '<task-label>' \
  --timeout 1h \
  --heartbeat 60 \
  --stale-after 180 \
  --output-log "$process_log" \
  --event-log "$event_log" \
  -- '<command>' '<args>'
```

单引号中的 label 和 command 是调用时替换的示例参数，不写入日志密钥。短命令可使用更短超时，不必创建正式
`log` 技能日志。`run-guarded.sh` 不可用或平台不兼容时，使用当前系统可用的 `timeout`/任务运行器超时，
并手动输出等价心跳；无法提供任何硬上限时不得声称已遵守本技能。

### Step 2. 启动长任务并持续判断健康度

长任务至少输出以下生命周期记录：

```text
[rule] event=start label=<label> pid=<pid> timeout=<duration> heartbeat=<duration>
[rule] event=progress label=<label> phase=<phase> progress=<n/m> eta=<duration>
[rule] event=resource label=<label> elapsed=<duration> cpu=<percent> rss=<size> gpu=<usage> disk=<size>
[rule] event=checkpoint label=<label> path=<path> completed=<n>
[rule] event=exit label=<label> status=<exit-code> elapsed=<duration>
```

健康判断同时满足以下条件才算正常：

1. 任务级进度在 `stale_after` 内更新；
2. 资源占用稳定在预算内，没有持续增长的内存、失控子进程、磁盘写满或异常 IO；
3. 日志没有重复错误、重试风暴或无意义刷屏；
4. 当前耗时没有明显突破 `soft_deadline` 且 ETA 仍可由实际进度解释。

只看到心跳而进度长期不变时，判定为“存活但停滞”；只有进度增长但资源异常时，判定为“有进展但需限流”。
两种情况都不得继续无界等待。

### Step 3. 中断不良进程并闭环处理

发现超时、停滞、资源越界或重复错误时：

1. 保存最后一段日志、PID、子进程、资源指标、当前检查点和退出原因；
2. 判断进程是否可续接；可续接下载、服务或带检查点计算优先保留或发送暂停信号；
3. 发送温和终止信号 `TERM`，等待进程清理和检查点落盘；
4. 超过宽限期仍未退出时，终止整个进程组并确认 PID 消失；
5. 清理残留子进程、临时文件和锁，但保留复现与诊断证据；
6. 进入 `debug` 定位根因；确认正确性后进入 `optim` 处理性能或资源问题；
7. 用更新后的预算和验证判据重跑，不从失败点盲目继续。

禁止只因为“运行慢”就终止持续产出有效结果的健康任务；也禁止为了保进度而放任已明确停滞、越界或错误的
进程继续消耗资源。

### Step 4. 共享环境与调度作业执行

共享环境默认采用：

```bash
nice -n 10 env \
  OMP_NUM_THREADS=1 \
  OPENBLAS_NUM_THREADS=1 \
  MKL_NUM_THREADS=1 \
  NUMEXPR_NUM_THREADS=1 \
  '<command>' '<args>'
```

需要多线程时显式提升到任务所需的最小值。可用 `ionice` 时同时降低 IO 优先级；临时数据写入任务拥有的工作区
或集群 scratch，并在结束、失败和过期时清理。登录节点只执行文件检查、轻量构建、提交和短时监控；重计算、
大批量测试、数据库导入和 GPU 工作进入调度器。

调度作业提交前检查队列、分区、现有作业和配额：

```bash
squeue -u "$USER" -o '%.12i %.30j %.10P %.10T %.12M %.10l %R'
sinfo -s
scontrol show partition '<partition>'
```

提交脚本必须显式包含作业名、partition/queue、time、nodes、ntasks、cpus-per-task、memory、GPU、输出和错误
日志；实际参数按 `references/process-and-resources.md` 的资源规格校准流程确定。提交后记录 job id，限制同时排队和
运行的同任务作业数，持续检查状态与资源效率；发现异常时 `scancel` 该作业，不批量取消无关作业。

若任务确实需要大量 CPU、GPU、内存、存储或机时，先用试跑与算法复杂度证明资源需求，再按完整规模分配。
若当前配额无法满足且降规模会损害正确性或质量，报告资源阻塞和最小所需预算；不得静默截断任务。

### Step 5. 判断阶段成果能否自动交付

阶段成果完成后，先执行完整验收与交付检查，再决定是否提交：

1. 本次会话的相关测试、语法检查、lint/typecheck 和回归均通过；
2. `git diff --check` 为零，改动仅限本阶段范围，无冲突标记、调试残留或无关文件；
3. 未暂存敏感信息、凭据、环境变量原值、超大文件或不应入库的二进制；
4. `log` 已写入阶段或最终日志，并在日志中包含关键证据和用户报告；
5. 当前分支、远程分支和仓库状态均可判定，且不存在未完成的 merge/rebase/bisect；
6. `git fetch` 后远程目标分支可 fast-forward 到当前工作，不存在需要强推或历史改写的分叉；
7. 自动后续步骤不会删除、覆盖或提交其他用户/agent 的未预期改动。

满足全部条件时，按以下顺序执行：

```bash
repo_root=$(git rev-parse --show-toplevel)
branch=$(git -C "$repo_root" branch --show-current)

git -C "$repo_root" fetch --prune origin
git -C "$repo_root" merge-base --is-ancestor "refs/remotes/origin/$branch" HEAD
git -C "$repo_root" diff --check

# 只暂存本任务明确文件，禁止 git add -A / git add .
git -C "$repo_root" add -- path/to/file-a path/to/file-b
git -C "$repo_root" diff --cached --check
"$RULE_SKILL_DIR/../form/scripts/form-large-files-check.sh" --root "$repo_root"
git -C "$repo_root" diff --cached --stat
git -C "$repo_root" commit -m '<type(scope): 阶段成果说明>'
git -C "$repo_root" push origin "$branch"
```

提交前必须逐个核对暂存路径和暂存 diff。任一闸门失败时停止，不提交、不推送；已通过的问题修复并重新验证后
再从 Step 5 开始。推送失败时保留本地提交并报告认证或远程状态，不虚报远程完成。

标签不是每次提交的默认动作。仅在存在明确、非破坏性的版本语义时调用 `tag` 技能：

- 进行中的可复用快照 → `dev`；
- 已稳定完成的里程碑 → `stab`；
- 已修复并验证的缺陷 → `bug`；
- 测试体系或重要回归完成 → `test`。

标签类型不明确、历史链自检失败、目标提交不一致或远程对象漂移时不打标签。本技能的条件式授权允许推送本次
新建的非破坏性标签，但不允许 force push、删除标签或改写已推送标签。

如果标签已在本地创建，且范围、验证、日志、安全、大小和远程 fast-forward 闸门仍全部通过，交付尚未完成：

```bash
git push origin "$branch"
git push origin "$NEW_TAG"
git ls-remote origin "refs/heads/$branch" "refs/tags/$NEW_TAG" "refs/tags/$NEW_TAG^{}"
```

只有远端分支和标签对象均与本地一致时，才能报告已同步。不得把本地提交或标签的“未推送”状态作为条件满足时
的最终交接。

### Step 6. 输出阶段摘要

```text
✓ rule 门控完成
   环境: <独占/共享/调度/子 agent>
   进程: <label、预算、是否超时、最终退出码>
   进度: <心跳/阶段进度/检查点/停滞证据>
   资源: <CPU/RSS/GPU/磁盘/并发摘要>
   处置: <正常/限流/TERM/KILL/debug/optim>
   Git: <未提交/已提交未推送及原因/已推送/未授权或未满足闸门>
   标签: <类型与名称及本地或远端状态/未创建及原因>
   日志: <process/event/log 技能日志路径>
```

声明“完成”“通过”“已推送”前，逐项核对本次会话刚产生的超时状态、退出码、测试输出、Git 状态和远程
分支状态；缺失证据的项标为“未验证”或补跑。

## 错误处理

| 场景 | 处理 |
|---|---|
| 启动前无法给出有限超时 | 不启动；拆分任务、先做有界试跑，或报告阻塞 |
| 预计超过 10 分钟但没有进度信号 | 不启动；增加阶段输出、进度文件、检查点或 `run-guarded.sh` |
| 工具不支持超时参数 | 使用操作系统 `timeout`/调度器时限；两者都不可用时报告无法执行硬限 |
| 心跳存在但任务进度停滞 | 收集进程树、资源、日志和检查点；按阈值 TERM，宽限后 KILL，再 debug/optim |
| 内存持续增长或磁盘快速耗尽 | 立即限流或终止，保留证据；定位泄漏、缓存无界或输出路径错误 |
| 进程已超时但子进程仍存活 | 终止整个进程组并确认 PID 消失，清理锁和临时文件 |
| 共享环境无法确认 | 按共享环境处理；降线程、降并发、低优先级，重任务转调度器 |
| 登录节点出现重计算 | 停止并迁移到调度器；仅保留轻量编排和监控 |
| 调度作业缺少 time/resource 限制 | 不提交；补齐 partition、time、CPU、内存、GPU 和输出路径 |
| 排队过多或重复提交 | 先查看 `squeue`，合并/取消本任务重复作业，限制同任务并发 |
| 实际任务需要大资源 | 以试跑和复杂度证明需求，申请足够预算完整执行；配额不足则报告阻塞 |
| 为省资源导致精度、规模或验证下降 | 恢复必要资源或停止，不接受不完整结果 |
| 阶段测试失败或有未验证项 | 不提交；先 debug、测试和复查 |
| 存在无关改动或他人未提交内容 | 只检查不覆盖；无法安全隔离时停止自动交付 |
| 远程分支已分叉或需要强推 | 不自动推送；报告分叉并等待安全的非破坏性处理 |
| push/tag push 认证失败 | 保留本地提交或标签，报告失败命令和远程未更新事实 |
| 本地提交或标签未推送但全部闸门通过 | 继续推送分支和本次新标签并回读验证，不以“如需同步”交给用户 |
| 标签类型不明确或链自检失败 | 跳过标签，不猜测类型，不改写历史 |
| 命中敏感信息或大文件闸门 | 停止该批提交和推送，清理问题后重新验证 |
| `run-guarded.sh` 缺失或不兼容 | 使用等价原生超时与心跳；无法满足硬限时停止并说明 |
| 用户明确关闭 rule | 当前任务停用本技能流程；更高优先级安全边界仍有效 |

## 注意事项

- `>10 分钟` 是强制可观测阈值，不是等待 10 分钟后才检查的期限；启动时就应配置进度与停滞判据。
- 进程日志与正式任务日志职责不同：前者用于运行监控，后者由 `log` 归档；只有后者默认进入 Git 日志。
- 共享环境的核心不是平均使用，而是不因单个 agent 的突发负载影响其他用户；资源空闲也不能成为无限占用的理由。
- 节省资源与保证任务质量冲突时，优先保证正确、完整、可验证的结果，并明确资源依据。
- 自动交付是严格条件下才生效的例外，不扩展到破坏性 Git 操作、系统配置、凭据、仓库外路径或用户明确禁止的范围。
- `rule` 常驻不意味着反复输出相同提醒；只在预算建立、异常处置和阶段交付时给出门控证据。
- 从其他技能抽取的规则只保留可泛化的治理约束，不复制各技能的专业工作流；来源映射见
  `references/extracted-rules.md`。
