# 纵向切片与阻塞边

## 1. 默认使用 tracer bullet

每个任务优先切成一条窄但完整的纵向路径，贯穿所需的数据、接口、实现、测试和可见结果，而不是按“数据库层、服务层、
UI 层”横向拆成若干无法独立验证的阶段。

一个合格任务：

- 完成后能演示或验证一个端到端行为；
- 能在一个新的 agent 上下文中完成；
- 自带通过/失败断言；
- 只声明真正的阻塞依赖。

## 2. 阻塞边

为每个任务写 `Blocked by`：

- 没有阻塞时写 `None (can start immediately)`；
- 只列会阻止本任务开始的前置任务，不把“相关”“同属一个功能”误写成阻塞；
- 依赖图应允许识别当前 frontier：所有 blocker 已完成的任务即可执行。

## 3. 预重构

如果一项机械整理能显著降低后续实现难度，把它作为前置任务，例如引入 seam、稳定接口、移除重复分支或补齐行为测试。
预重构只服务于即将到来的变更，不做无关架构美化。

## 4. 宽重构例外

跨越大量调用方的机械重命名、类型替换或接口迁移，若无法用单个纵向切片保持全绿，改用 expand-contract：

1. expand：并排加入新形式，旧形式保持可用；
2. migrate：按包、目录或其他可验证边界分批迁移调用方；
3. contract：确认无旧调用方后删除旧形式。

每个迁移批次都必须有独立验证；最终 integrate 任务只负责跨批次的共同验证，不掩盖局部失败。

## 5. 领域词汇与深模块

任务标题和接口使用仓库现有领域词汇。若术语冲突，先在计划中统一；若模块接口既大又薄，优先收窄 interface，
把复杂度藏到 implementation 后面。删除模块测试：若删除后复杂度没有回到调用方，该模块可能只是 pass-through。

## 6. 自审

- [ ] 每个任务都是可独立验证的纵向切片，宽重构已使用 expand-contract；
- [ ] 每个任务都有 `Blocked by`，依赖只表达真实门槛；
- [ ] 预重构先于依赖它的功能任务；
- [ ] 任务名、接口名和领域词汇一致；
- [ ] 每个任务能在单个新上下文内完成并验证。
