# 双轴审查与 AI 残留检查

## 1. 两条轴分开报告

每次实质审查至少区分：

- **Standards**：改动是否遵守仓库已文档化的命名、目录、测试、安全和接口约定；
- **Spec**：改动是否完整实现原始需求，是否夹带未要求行为，是否存在“看似实现但语义错误”。

两条轴独立结论，不先跨轴合并或只选一个总冠军。一个改动可能同时“规范正确但实现错”或“需求正确但违反约定”。

## 2. 证据等级

每条发现标记：

- `确证`：由代码、测试、命令输出或文档原文直接证明；
- `推断`：证据一致但依赖未验证假设；
- `未验证`：当前环境无法检查。

审查结论必须附 `文件:行号`、命令或测试证据。严重度按对正确性、安全性和用户结果的影响分级：

- Critical：结果错误、数据损坏、安全边界突破或不可恢复副作用；
- Important：行为回归、接口违约、关键边界缺失或明显维护风险；
- Minor：局部可读性、重复、命名或低风险清理。

## 3. AI 残留与 fallback 分类

在改动范围内主动查找：

- 掩盖失败的 fallback、静默默认值、吞错、绕过校验和重复执行路径；
- 复制粘贴分支、死代码、仅在测试中使用的 wrapper、过度抽象；
- 调试输出、未使用配置、过时兼容层和无调用方接口；
- 声称成功但退出码非零、跳过测试、日志与状态矛盾的路径。

将 fallback 分成两类：

1. **掩盖型残留**：隐藏证据、绕过契约或增加未测试路径，应优先删除或回到根因修复；
2. **有依据的边界 fallback**：只位于外部依赖、版本兼容或故障安全边界，必须有原因、失败证据和主/备路径测试。

## 4. 审查顺序

1. 锁定 BASE/HEAD、spec 和仓库标准来源；
2. Standards 与 Spec 分别取证；
3. 先查 Critical 的正确性、安全性和数据生命周期，再查重复、死代码、命名和抽象；
4. 对每项发现给出影响、证据和建议修复方向；
5. 修复后重新运行原断言和全量回归，并确认旧问题已闭环。

## 5. 报告骨架

```text
Standards:
- <severity> <file:line> <确证/推断> <规则或气味> <影响> <修复>

Spec:
- <severity> <file:line> <确证/推断> <spec 要求或 scope creep> <影响> <修复>

Summary:
- Standards: <counts>; worst=<...>
- Spec: <counts>; worst=<...>
- Verification: <commands/results>
```
