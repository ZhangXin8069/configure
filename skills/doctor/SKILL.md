# doctor — 广域健康检查技能

## 执行前置

遵循当前目录 `AGENTS.md`「技能执行公共契约」；仅按需读取技能正文与 reference。

本 skill 默认只做本地、只读的巡检与分级报告：先盘点覆盖面，再做一致性、入口、权限、
语法和基本安全边界检查；发现问题时给出证据、影响面和后续技能建议，不擅自扩大为修复、
升级或外部调研。

## 核心原则

1. **体检优先于修补**：先确认目录、入口、镜像和权限是否健康，再决定是否需要 `debug`、
   `up`、`test` 或 `diff`。
2. **范围比单点更重要**：`doctor` 看的是 `skills/tools/hooks/plugins` 与 `.opencode/skills/`
   之间是否整体一致，而不是单个脚本是否能跑。
3. **证据要落到路径**：每个结论都要能回指到文件、目录、权限位、语法检查输出或清单差异。
4. **默认只读**：健康检查阶段不改文件；需要修复时先分流到对应技能或等待用户授权。
5. **先看入口，再看实现**：技能看 `SKILL.md`/`AGENTS.md`/镜像；脚本看 shebang、可执行位、
   参数入口；插件看 manifest、加载点和权限边界。
6. **把高风险问题单独标出**：语法错误、缺失入口、不可执行、镜像脱节、明显危险命令和
   权限过宽，不和普通一致性提示混在一起。
7. **覆盖度检查要双向**：既看“目录里有什么”，也看“登记里少了什么”，尤其是
   `.opencode/skills/` 和 `skills/AGENTS.md` 的漂移。
8. **只看本地，不做外部升级对照**：`doctor` 只做当前仓库健康扫描；需要外部最佳实践、
   热榜或生态对照时交给 `up`。

## Git 检查

有 Git 且本次会话产生文件改动时，执行 `git diff --check` 和定向复查；不自动暂存、提交或推送。
无 Git 或无本次改动时跳过。

## 触发时机

- 用户要求体检、巡检、健康检查、覆盖度检查、一致性诊断、入口异常排查、权限/语法核验或
  基础安全边界检查。
- 用户要检查 `skills/`、`tools/`、`hooks/`、`plugins/` 或 `.opencode/skills/` 是否同步、
  是否可用、是否有入口缺口。
- 用户怀疑技能树、脚本、钩子、插件“整体不对劲”，但还没到单点报错的程度。
- 与其他技能配合：单点报错/栈追踪 → `debug`；升级技能库/补登记/镜像同步 → `up`；
  需要重新生成目录结构 → `init`；需要对比改动 → `diff`；需要真正运行验证 → `test`；
  需要把发现的问题升级成计划 → `plan`。

## 工作流程

### Step 1. 定义巡检范围

1. 默认范围是当前 Git 根目录下的 `skills/`、`tools/`、`hooks/`、`plugins/` 以及
   `.opencode/skills/` 镜像；用户明确缩小范围时只收窄，不越界。
2. 输出一句**任务定义**：本次是做覆盖度盘点、一致性诊断，还是入口/权限/语法/安全边界核验。

### Step 2. 盘点覆盖面

1. 列出目录与文件：

```bash
git rev-parse --show-toplevel
rg --files skills .opencode/skills tools hooks plugins
find skills -mindepth 1 -maxdepth 1 -type d
find .opencode/skills -mindepth 1 -maxdepth 1 -type d
```

2. 对每个 `skills/<name>/` 核对：
   - `SKILL.md` 是否存在；
   - `AGENTS.md` 是否存在；
   - frontmatter 的 `name` 是否与目录名一致；
   - `description` 是否明确说明“做什么 + 何时使用”；
   - 是否包含触发时机、工作流程、错误处理、注意事项等固定章节；
   - `.opencode/skills/<name>/` 镜像是否存在且文件对得上。
3. 对 `tools/`、`hooks/`、`plugins/` 记录入口文件、清单文件、脚本文件和目录边界。
4. `skills/AGENTS.md` 的技能登记只做漂移比对，不在本 skill 中修改；如需补登记，转 `up`。

### Step 3. 核验入口、权限与语法

1. 对 shell 入口检查 shebang 和语法：

```bash
bash -n path/to/script.sh
sh -n path/to/script.sh
```

2. 对 Python 入口检查语法：

```bash
python3 -m py_compile path/to/script.py
```

3. 对 YAML/JSON/manifest 先做存在性与字段一致性检查；如果仓库里已有专用校验器，优先用现成校验器。
4. 对入口脚本、hook、plugin 加可执行位检查：
   - 入口文件是否有 `+x`；
   - shebang 是否和实际解释器匹配；
   - 软链接/包装脚本是否指向有效目标。

### Step 4. 做基础安全边界扫描

1. 只扫相关树里的高风险模式，不做外部联网审计。
2. 重点看：
   - 明显的远程执行拼接：`curl ... | bash`、`wget ... | sh`；
   - 直接 `eval` 未知输入；
   - `rm -rf`、`chmod 777`、`sudo` 等危险操作；
   - 泄露 token、密钥、私有路径或环境变量的输出；
   - 写出仓库边界之外的路径。
3. 把“风险存在”与“已被利用”分开写，避免把预警写成事实。

### Step 5. 汇总与分流

1. 输出四类结果：`healthy`、`drift`、`entry/perm`、`syntax`、`security`。
2. 每条问题都写清路径、证据、影响面和优先级。
3. 只给建议，不替用户决定修法；常见分流是：
   - 单点实现或脚本故障 → `debug`
   - 技能库登记、镜像、目录同步 → `up`
   - 多步骤整改方案 → `plan`
   - 需要复测或回归证明 → `test`
   - 需要改动审查 → `diff`

## 错误处理

| 场景 | 处理 |
|---|---|
| 缺少 `SKILL.md` / `AGENTS.md` / `.opencode` 镜像 | 记为覆盖度缺口，说明影响面，转 `up` 或 `init` 处理 |
| `name` 与目录名不一致 | 记为一致性缺口，列出文件路径与实际值，不在本 skill 中改 |
| shell 语法失败 | 记下文件和行号，转 `debug` |
| 入口文件不可执行或 shebang 不匹配 | 记为入口缺口，说明实际权限与解释器，转 `debug` 或 `up` |
| manifest / 清单字段缺失 | 记为结构缺口，优先补全后再谈运行，转 `up` |
| 发现明显危险命令或泄露风险 | 标为高风险，先报告证据，不扩大执行范围 |
| 没有合适的解析器或校验器 | 降低置信度，只做可用检查并如实说明限制 |
| 用户要求直接修复 | 先说明 `doctor` 默认只诊断不改，再切到对应技能 |

## 注意事项

- `doctor` 是日常体检，不是根因修复，也不是外部最佳实践调研。
- 与 `debug` 的区别：`doctor` 看面、看覆盖、看边界；`debug` 盯单点故障并修复。
- 与 `up` 的区别：`doctor` 只做本地健康诊断，不做热榜、外部对照或目录升级。
- 与 `plan` 的区别：`doctor` 先发现问题，不替代实现计划。
- 输出要短、准、可追溯；能落到路径和证据的才算结论。
