# follow-up — 日常跟进与交接技能

## 执行前置

遵循当前目录 `AGENTS.md`「技能执行公共契约」；仅按需读取 `go-on`、`plan`、`all`、`auto` 的 `SKILL.md`。
follow-up 只负责把信息压缩成可执行的运营包，不替代实现、调试或自动循环。

## 核心原则

1. **先压缩，再分发**：把原始输入压成少量稳定块，再决定下一步交给谁。
2. **行动项要可执行**：每条待办都用动词开头，并尽量附上依赖、验证方式和期望结果。
3. **状态与动作分离**：先说明现在到哪一步，再列下一步做什么，避免把两者混在一起。
4. **跨会话可续**：保留关键决策、阻塞点、已完成项和下次检查点，方便后续接手。
5. **不抢职责**：恢复现场交给 `go-on`，实现计划交给 `plan`，持续迭代交给 `all`，无人值守交给 `auto`。
6. **证据优先**：不确定的信息要标明来源和置信度，不能把猜测写成结论。
7. **最小外溢**：默认只产出摘要和清单，不额外扩写背景材料或扩大任务范围。
8. **便于复盘**：输出里要能看出做了什么、为何这么分、下一次从哪儿接。

## Git 检查

有 Git 且本次产生文件改动时，执行 `git diff --check` 和定向复查；不自动暂存、提交或推送。无 Git 或无本次改动时跳过。

## 触发时机

- 用户要求：日常跟进、待办拆解、交接、复盘、状态同步、周报/日结、行动项清单、信息压缩、跨会话延续
- 场景：把一段讨论整理成可执行摘要、把当前工作交给下一个人/下一个会话、把分散信息整理成下一步列表
- 与其他技能配合：恢复中断现场先用 `go-on`；需要实现路线时转 `plan`；需要并行拆分时转 `dispatch`；要真正推进并反复收敛时转 `all`；要无人值守执行时转 `auto`
- 不适用：代码调试、性能优化、实际实现、纯方案设计、会话恢复本身

## 工作流程

### Step 1. 收集输入

先确认当前目标、受众、截止时间、已知阻塞和要交付的形式。缺项一次问全，不分批追问。

### Step 2. 压缩成工作包

把信息整理成固定块：

- 任务定义
- 当前状态
- 已完成
- 进行中
- 阻塞/风险
- 下一步行动项
- 需要继续调用的技能

### Step 3. 生成行动项

每条行动项写成可执行句子，尽量带上：

- 目标
- 依赖
- 验证方式
- 优先级

如果需要拆成多个独立子任务，先标出可并行部分，再把执行交给 `dispatch`。

### Step 4. 路由下一步

- 恢复被中断的任务：转 `go-on`
- 需要实现计划：转 `plan`
- 需要持续迭代到更好：转 `all`
- 需要无人值守执行：转 `auto`

### Step 5. 自检

输出前检查：

1. 是否已经把原始信息压缩到足够短
2. 是否把不确定项标清楚
3. 是否没有把别的技能职责混进来
4. 是否能直接拿去交接或继续

## 错误处理

| 场景 | 处理 |
|---|---|
| 输入太散、目标不清 | 先归类再追问；缺项一次性问全 |
| 用户其实要恢复中断任务 | 先转 `go-on`，再回到 follow-up 做摘要与行动项 |
| 用户其实要实现方案 | 先转 `plan`，不要在这里写实现细节 |
| 用户其实要执行与迭代 | 先转 `all` 或 `auto`，不要重复编排流程 |
| 信息里存在冲突 | 保留冲突并标注来源，不擅自裁决 |

## 注意事项

- 默认输出应短、清楚、可交接
- 不要把复盘写成散文，也不要把待办写成长段解释
- 不主动写入仓库文件，除非用户明确要求落盘
