**总体判断**

本库完整配置的优势是流程治理、可审计性和复杂任务保障，不是短程代码生成质量；劣势是固定的上下文与流程成本很高。在这批 16 道 HumanEval 上，两臂都 16/16 正确，但完整配置使用约 10 倍 token、约 2 倍墙钟时间，没有测到正确率增益。

**优势**

- 流程完整。完整配置会加载 `auto/all/log`，部分任务再按需加载 `test/make/diff`，并执行目标管理、Git 检查、验证和日志归档。它更像一套可审计的交付流程，而不是一次性代码补全。
- 可追溯性强。16/16 次完整配置运行都生成了最终日志，共 16 份、82,389 bytes；原生臂没有这些治理产物。对需要复盘、交接或合规的任务，这是实际价值。
- 验证动作更多。完整配置平均执行 20.4 个命令，原生为 5.6 个；测试相关命令总计 63 对 33。虽然本样本没有转化为更高通过率，但复杂任务中更可能提前暴露回归、路径错误和边界问题。
- 安全与范围控制更完整。`rule`、Git 边界、超时和日志约束适合无人值守、长任务和高风险改动；本次正式实验完整配置臂 0 超时、0 越界文件写入。
- 复杂任务的可扩展性更高。自动技能路由、计划、debug/optim 循环、恢复和资源预算在短题中没有充分发挥，但在多文件、长上下文和中断恢复场景中具有潜在收益。

**劣势**

- Token 成本过高。完整配置平均 385,666 total tokens/题，原生 38,513；聚合为 10.01 倍。未缓存输入仍为 9.44 倍，输出 token 为 4.96 倍，不能仅用缓存折扣解释。
- 上下文重复回放明显。完整配置命令输出约 512KB，原生约 16KB，相差约 31 倍。16 次运行全部读取 `auto`、`all`、`log` 三份技能正文，单是这三份文档合计约 48.7KB，且工具回合会重复携带已有上下文。
- 工具回合过多。完整配置平均 20.4 个命令，原生命中 5.6 个；Git 命令 117 对 20，目标管理命令 15 对 0，日志相关命令 31 对 0。完整配置命令数与 token 的 Pearson 相关系数为 0.8525，说明流程步数直接放大了上下文成本。
- 耗时更高。平均 185.6 秒对 94.1 秒，聚合为 1.97 倍；中位数 186.2 秒对 83.6 秒，为 2.23 倍；完整配置在 13/16 题更慢、3/16 更快。
- 短任务存在过度编排。HumanEval 只需修改一个 `solution.py`，完整配置仍执行目标、审计、Git 和日志流程。完整配置每个工作区有 4 个常规文件，原生平均 2.56 个，主要是额外日志契约。
- 正确率收益未显现。两臂都是 16/16，Wilson 95% 区间均为 80.64%–100%；这是模型在该样本上的正确率天花板，不是完整配置等同或更差的普遍证明，但至少说明这批短题无法证明其质量收益。
- 输出更冗长。Agent 消息从原生平均 480.6 bytes 增至 1,239.5 bytes， reasoning item 从 4.56 增至 12.63 个。模型把更多输出花在计划、状态和收尾说明上。

**适用边界**

| 场景 | 更优选择 | 原因 |
|---|---|---|
| 单文件、一次性、规格明确、测试直接 | 原生最小提示 | 固定流程没有质量收益，token 和时间成本显著更低 |
| 批量算法题或代码补全 | 原生最小提示 | 成本按任务数线性放大，完整配置的固定开销难以摊销 |
| 多文件仓库修改、需求有歧义 | 本库完整配置 | 计划、范围控制、测试与日志更可能降低返工 |
| 高风险、无人值守、需要审计 | 本库完整配置 | 主要价值是防错、恢复、记录和交付证据 |
| 长任务、需要中断续跑 | 本库完整配置 | 目标状态、恢复机制和资源门控有独立价值 |
| 成本敏感的重复子任务 | 混合方案 | 父任务使用完整配置做分解，子任务使用最小提示执行 |

**成本归因**

完整配置的额外 token 主要不是“写更多代码”，而是每次都建立完整工作协议：

- 每臂平均读取 3.875 份技能正文。
- 16/16 读取 `auto`、`all`、`log`；5 次读取 `test`，5 次读取 `make`，4 次读取 `diff`。
- 平均命令输出 31,984 bytes，原生为 1,025 bytes。
- 平均执行 7.3 个 Git 命令，原生命中约 1.25 个。
- 每题平均生成约 5.1KB 最终日志。

这些机制在复杂任务中可能换来可靠性和可审计性，但在 HumanEval 上只形成固定成本，因为最终仍然只需一个函数实现。

**改进优先级**

1. 增加复杂度分流。对单文件、短规格、已有明确测试的任务使用快速路径，不默认启动 `auto+all`。
2. 技能懒加载并压缩入口。保留技能路由摘要，只有触发对应阶段时才读取完整 `SKILL.md`；优先减少每次固定读取 `auto/all/log`。
3. 子任务默认使用精简契约。父 agent 负责计划和验收，子 agent 只接收目标、边界、测试和输出格式。
4. 日志批处理。批量短任务只生成一份批次日志，避免每题创建日志、更新索引并再次回放日志内容。
5. 控制说明性输出。限制中间计划、重复状态和收尾文字，保留最终结果与关键验证证据。
6. 用更难的基准验证收益。下一步应测试 SWE-bench Verified 或 Terminal-Bench；只有复杂任务正确率、返工率或恢复率提升，才能抵消约 10 倍的 token 成本。

**结论**

完整配置是“流程可靠性工具”，不是“所有任务都更快更省的通用加速器”。短任务应使用最小提示；复杂、高风险、需要审计和恢复的任务才值得完整配置。当前最值得优化的不是单个技能，而是缺少按任务复杂度自动切换的轻量执行档位。
