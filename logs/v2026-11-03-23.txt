--- report begin ---
结论：这不是 `cm` 启动器或 BYOK 配置的问题，而是 Command Code CLI 自身的账号认证门。`cm go` 只是把 `opencode-go` 合并进 `~/.commandcode/providers.json` 并以 `--skip-onboarding` 启动，它不提供 Command Code 账号凭据。

已确认的机制（CLI v1.88.2）：交互式启动无条件执行 `requireAuth → ensureAuthenticated → ensureCommandAuthenticated`；密钥来源先取环境变量 `COMMAND_CODE_API_KEY`，再读 `~/.commandcode/auth.json` 的 `apiKey`。`isLocalOnly()` 不参与这道门，因此 `--local-only` 不能免登录。

隔离 HOME 实测：无 `auth.json` 时 TUI 必然显示 `✔ Ready to log in / Sign in to Command Code`；`-p --local-only` 无 key 报 `Not authenticated`，假 key 报 `Authentication failed`；补上真实账号密钥后，print 与 TUI 两条路径都直接通过。

另一台机器的处理（任选其一）：
1) 正常登录一次：`command-code login`（或 `cmd login`），完成后 auth.json 落盘即永久生效；
2) 或继续用环境变量：在 `~/env-key.sh` 增加 `export COMMAND_CODE_API_KEY='<账号 key>'` 后 `source ~/env-key.sh`。注意这必须是 Command Code 账号 key（`user_` 前缀），BYOK 的 `OPENCODE_GO_API_KEY` 不能替代。

关于 env-key.sh 的硬性约束，当前状态是安全的：`/root` 不是 Git 仓库，`env-key.sh` 不在任何仓库内，也未被跟踪；已跟踪的 2672 个文件中未扫到任何真实密钥值。

已补两道防线：
- `/root/.config/git/ignore` 增加 `env-key.sh`、`env-key.*`、`.env-key`、`.env-key.*` 全局忽略；
- `/root/configure/.git/hooks/pre-commit` 拦截任何含密钥文件名的提交，专门兜住 `git add -f` 与仓库内 `!` 否定规则这两条绕过路径。

实测：加固前 `git add -A` 会捕获 `env-key.sh`；加固后 check-ignore 全部命中，`normal.sh` 不受影响；hook 对含密钥提交返回 exit=1，移除后正常提交 exit=0。

未验证项：另一台机器执行修复后的端到端结果，需在其机器上确认。
