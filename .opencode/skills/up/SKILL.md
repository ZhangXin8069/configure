# up — 技能库升级技能

## TODO 管理（全局约定）

执行第一步用 **todowrite 工具**生成**详细 TODO 列表**：按任务分解为可独立验证的
子步骤、按依赖排序；**每完成一个子步骤立即调用 todowrite 更新状态**（进行中/完成）；
收尾时核对全部完成。约定全文见 `skills/AGENTS.md`「TODO 生成与实时更新约定」。

把"技能库持续更新"固化为可重复流程：本地基线调查 → GitHub 最佳实践调研（重试至成功）→
差距分析 → 执行（优化/补充/新增/debug）→ 验证 → 收敛评估 → 升级汇总。
借鉴来源（anthropics/skills、obra/superpowers writing-skills 等）必须注明出处。

## 核心原则

1. **本地基线先行**：先只读检查本目录全部技能（目录完整性/格式/一致性/占位符），
   掌握现状后再谈升级；不调查就升级是臆断。
2. **网络调研重试至成功**：GitHub 引入是明确要求时，连接失败**一直重试**（换 raw/
   github.com 页面/调整超时），直至成功或用户终止；每次失败记录原因与重试次数。
3. **差距分析证据驱动**：逐条对照（现状 vs 最佳实践）形成差距表，只升级有实据的差距；
   不编造"最佳实践"内容，借鉴内容注明来源仓库与技能名。
4. **最小改动**：优化只改差距所在处，遵循本目录既有格式（frontmatter+核心原则+
   会话日志+历史日志预读+触发时机+工作流程+错误处理+注意事项）；补充=加缺失内容；
   新增=新技能目录（SKILL.md + AGENTS.md）；debug=修发现的问题（格式/完整性/逻辑）。
5. **验证闭环**：每处改动后验证——frontmatter 完整、name 与目录一致、无占位符、
   结构节齐备、行数合理；新增技能附目录 AGENTS.md 并登记技能表。
6. **收敛判定**：全部差距处理完毕（无剩余差距）或连续两轮无实质变化即收敛；
   收益微小（如措辞级改动）时报告权衡由用户取舍，不无限扩大范围。
7. **诚实原则**：无法获取/无法落实的差距如实报告（含原因），不虚报"已引入"。
8. **元升级（up 适用于自身）**：升级 up 技能自身时，把"反思 up 的差距"作为
   差距分析的第一行——本技能同样受基线调查、最小改动、验证闭环约束，
   不因"元"而豁免。

## 会话日志

每次 up 会话必须在**当前工作目录（技能库根）**生成详细日志：

- 文件名格式：`.up.<时间戳>.log`（例如 `.up.2026-08-14-01-12-38.log`）
- 时间戳格式：`%Y-%m-%d-%H-%M-%S`：`TS=$(date +%Y-%m-%d-%H-%M-%S)`
- 日志**不入库**（与仓库 `.agent.*.log`、`.all.*.log` 等约定一致），全程**追加**写入（`>>`）
- 记录内容（**会话头**）：开始时间、工作目录、git 分支与 HEAD、任务定义与升级目标；
- 记录内容（**过程**）：本地基线检查结果；GitHub 调研（来源 URL、获取成败、重试次数、
  失败原因）；差距分析表（技能 | 对应最佳实践 | 差距 | 动作）；每处改动
  （`文件:行号` + 说明）；验证结果；用户决策记录；
- 记录内容（**会话尾**）：升级汇总（优化/补充/新增/debug 各多少）、来源清单、
  遗留项、结束时间与总耗时。

**记录规范**：关键事件以分隔行标记 `---- [YYYY-MM-DD HH:MM:SS] 事件描述 ----`；
命令统一记作 `$ <命令>` 并在结果行标注退出码；全程不覆盖、只追加。

## 历史日志预读（关键信息速览）

会话**第一步**只读预读本技能**最新一份**历史日志的**尾部汇总区**（只关注关键信息，不做深入解析）：

```bash
tail -20 "$(ls -1t .up.*.log 2>/dev/null | head -1)"        # 尾部汇总区：上次任务/结论/遗留项
```

- 关键信息：① 上次任务/对象；② 结论或收敛结果；③ 遗留项与下一步建议——其余（过程轮次、命令细节）一律跳过，不做深入 think
- 约束：只读不改；无历史日志（首次运行）时正常跳过，不视为错误；总耗时以秒级为限

## 触发时机

- 用户要求升级技能库："升级技能库"、"更新skill"、"优化skill库"、"整理技能"、"up"
- 用户要求引入外部最佳实践："引入github最佳skill"、"参考github改进"、
  "吸收社区方法论"、"引入外部skill"
- 用户要求检查/修补技能："补充skill"、"技能库过时"、"技能没触发"、"skill有问题"
- 与其他技能配合：优化单个 skill 自身 → skill-creator；技能触发/行为异常 → debug；
  纯性能问题 → optim；升级后打标签 → tag；升级后查看改动 → diff；
  需要反复迭代至最佳 → all（up 可作为 all 的子流程）

## 工作流程

### Step 1. 解析升级目标

确认：升级范围（全部/指定技能）、是否引入 GitHub 最佳实践（网络重试策略）、
收敛标准（差距表清零/用户满意）。输出一句**任务定义**并记录到日志。

### Step 2. 本地基线调查（只读）

```bash
for d in */; do d=${d%/}; [ -f "$d/SKILL.md" ] || echo "MISSING SKILL.md: $d"; \
  [ -f "$d/AGENTS.md" ] || echo "MISSING AGENTS.md: $d"; done
# frontmatter name 与目录名一致性；占位符扫描；技能表与目录一致
grep -rn "TBD\|TODO" */SKILL.md 2>/dev/null || echo "无占位符 OK"
```

- 记录：目录完整性、frontmatter 一致性、占位符、技能表登记情况。

### Step 3. GitHub 最佳实践调研（失败一直重试）

```bash
# 首选 raw 文件（干净文本）；超时/失败换 github.com 页面；仍失败再试并加长超时
webfetch https://raw.githubusercontent.com/<owner>/<repo>/main/skills/<name>/SKILL.md
```

- 来源候选：anthropics/skills（官方）、obra/superpowers（社区方法论）、
  agentskills.io（规范）等，按相关性选择；
- **重试策略**：连接失败不停止——重试直至成功或用户终止；每次失败记录
  （URL、错误、第 N 次重试）；换路径（raw → 页面 → 加超时）再试；
- 记录获取成功的来源清单（URL + 技能名 + 吸收要点）。

### Step 4. 差距分析（对照表）

逐条对照形成差距表：

| 本目录技能 | GitHub 对应最佳实践 | 差距 | 动作（优化/补充/新增/debug） |
|---|---|---|---|

- 只列入有实据的差距；已覆盖的方法论标"已覆盖"不动作；
- 无对应技能且确有价值 → 列为"新增"候选，评估后再建。

### Step 5. 执行（最小改动）

按差距表逐项处理，遵循本目录既有格式约定：

1. **优化**：改差距所在处，不重构无关部分；
2. **补充**：在既有技能对应章节加入缺失内容（注明来源）；
3. **新增**：新建 `skills/<name>/SKILL.md` + `AGENTS.md`（3-7 行），
   更新 `skills/AGENTS.md` 技能表登记；
4. **debug**：修复发现的格式/完整性/逻辑问题；
5. 借鉴内容**注明出处**（仓库 + 技能名），不照搬不署名。

### Step 6. 验证

每处改动后核验（**结构验证必做，行为验证按改动性质做**）：

1. **结构验证**（每次必做）：frontmatter 完整（name/description/metadata）、
   name 与目录一致、无占位符、结构节齐备、SKILL.md 行数合理（参考 <500 行
   分级披露）、技能表登记正确；
2. **触发描述检查**（每次必做，吸收 writing-skills SDO）：description 以
   触发条件为主（"当用户要求…" + 具体触发词/场景），**不得总结工作流**——
   描述总结工作流时 agent 可能只按描述执行而跳过正文（SDO 实测结论）；
   发现违规即在差距表登记并精简，工作流细节留在正文；触发词覆盖"pushy"
   （对抗少触发倾向）；
3. **行为验证**（新增/大改技能必做，纯措辞级改动可选）：用 2-3 个真实用户
   口吻的测试提示词试跑该技能的指令路径——命令是否真实可执行、步骤是否无歧义、
   触发描述是否覆盖触发场景（吸收 writing-skills 的 TDD 式技能测试思想；
   完整有/无技能对照评估转 skill-creator）；
4. **修改回归**（修改既有技能后必做）：`git diff` 复查改动仅含预期内容，
   未破坏原结构（冲突标记/意外删除/格式破坏检查）；
5. 验证结果逐项记录到日志，不虚报"已验证"。

### Step 7. 收敛评估

- 差距表全部动作完成且验证通过 → 收敛，进入 Step 8；
- 存在未落实差距（如网络失败被用户终止）→ 如实列入遗留项；
- 收益微小项报告权衡，由用户决定取舍。

### Step 8. 总结（结构化输出）

```text
✓ up 升级完成
   目标:   <任务定义>
   来源:   <引入的 GitHub 来源清单（URL + 技能名），重试 N 次成功>
   差距:   <N 项差距全部处理 / 遗留 M 项>
   优化:   <技能名: 文件:行号 <说明>，无则省略>
   补充:   <同上>
   新增:   <技能名: 文件:行号 <说明>，无则省略>
   debug:  <同上>
   验证:   <检查项逐项通过情况>
   收敛:   <差距表清零/收益微小/用户终止>
   遗留:   <未落实项/待用户确认项，无则省略>
   日志:   .up.2026-08-14-01-12-38.log
```

## 反合理化表（跳过验证/直接动手的借口 → 现实）

| 借口 | 现实 |
|---|---|
| "这个技能明显没问题，不用验证" | 你清楚 ≠ agent 清楚；未验证的技能必然有问题（writing-skills 实测结论） |
| "只是加一小节，不用试跑" | 新指令路径同样可能不可执行/有歧义；试跑只要几分钟 |
| "上次验证过了，这次不用" | 每次改动都是新状态；修改回归检查成本极低 |
| "GitHub 上写的肯定对" | 外部实践需适配本目录格式与触发机制，适配即需验证 |
| "结构检查就够了" | 结构完整 ≠ 行为正确；新增/大改技能必做行为试跑 |
| "时间紧，先升级再说" | 未验证的升级部署后修复成本更高（同 TDD 反合理化） |

**以上任一出现 = 停下，补验证。**

## 错误处理

| 场景 | 处理 |
|---|---|
| 升级范围不明确 | **一次性列出全部候选**（全部技能/指定技能/仅引入外部实践）提问，不逐次追问 |
| GitHub 连接失败 | 一直重试（raw→页面→加长超时），记录重试次数；用户终止才停 |
| 目标技能不存在 | 报告并列出候选，不臆造 |
| 差距无实据 | 不动作；记录"已覆盖"结论 |
| 借鉴内容无法确认 | 不引用；报告来源不可靠 |
| 新增技能与既有技能职责重叠 | 指出重叠，建议合并/引用或明确边界 |
| 验证失败（frontmatter/占位符/行为试跑） | 按失败项修复后复验（循环至通过） |
| 修改破坏原结构（diff 复查发现问题） | 回退/修正改动，重新验证 |
| 用户中途改变范围 | 重新解析目标，日志登记变更 |
| 收益微小 | 报告权衡，由用户决定取舍 |

## 注意事项

- 本地基线、差距表、验证结果均以实测为准，不编造；
- 网络重试按用户要求执行直至成功，但向用户报告重试进展；
- 借鉴外部实践注明出处（仓库 + 技能名），不照搬不署名；
- 不提交代码、不删除文件（用户未明确要求时）；涉及 git 跟踪文件时提示用户自行提交；
- 不越界访问工作目录之外的内容；
- 会话日志 `.up.<时间戳>.log` 不入库，由用户决定保留或清理。
